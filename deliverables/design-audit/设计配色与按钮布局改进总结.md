### 1.1 补充：「医器云」系统专项说明（应补充请求新增）

> 说明：该作品页为纯图片画廊，正文无独立设计说明文字，WebFetch 只能取到页头元信息，无法读取图片像素级配色与图片内嵌的设计思路文字。以下先列出**可确认元数据**，再基于「医疗器械 SaaS」品类的通用设计语言做**对标补充**（标注为推断），逐图真实配色需在浏览器人工核对原图。

**① 可确认元数据（来自页面抓取）**
- 作品名：SaaS 产品-「医器云」系统
- 作者：Andy丶子陌（北京 / UI 设计师；站酷**推荐设计师** + **终身会员** + **PRO 计划**）
- 数据：2 年前发布，4409 浏览
- 品类：医疗器械行业 SaaS（B 端中后台系统）

**② 医疗器械 SaaS 的通用设计语言（对标补充 · 推断依据：行业配色心理学 + B 端色彩体系共识）**
- **配色心理**：临床/医疗场景普遍采用冷色系（蓝 / 青 / 绿）+ 大量中性灰白，传递「洁净、可信、冷静」。其中**绿色**象征生命/平衡/安心——这与本项目「薄荷绿平台色」的心理暗示高度契合，说明平台选绿色作品牌色方向是对的。
- **信息密度**：B 端工具属性强，界面以「表格 + 表单 + 数据卡片」为主，强调信息分层与高效检索，而非视觉噱头；按钮多为中小组件，圆角克制。
- **功能色即安全色**：在医疗/工业语境里，红/黄/绿的状态色往往是「功能性编码」（告警/警告/正常），必须具备**高对比、强一致性**。这是此类 SaaS 对配色一致性的要求远高于普通 C 端的原因。
- **与本项目关联**：本项目的薄荷绿平台色在心理层面与医疗器械 SaaS 的绿色语义一致，方向正确；但当前配色令牌被 5+ 来源重定义（含近黑 `#0f172a`、蓝 `#2563eb`、紫/橙残留），等于把「安全编码色」做成了随机值——对可能服务医疗/工业垂直领域的 SaaS 而言，风险被放大。因此 **P0 统一令牌**的优先级不仅不低，反而因品类属性更高。

**③ 给本项目的启示**
- 保留单一薄荷绿作为平台主色（与医疗绿语义自洽），但必须消灭「同 token 不同值」「硬编码蓝/紫/橙」的乱象，否则功能色会失去安全编码意义。
- 表单/表格密集型页面是本项目与「医器云」最相似的形态，应优先应用报告第三节的「按钮收敛 + 长表格提效 + 就地管理」规范。

### 2. 文章《企业级 SaaS「工作台」的设计观察》（群核科技 MCUX，内容最丰富）

核心可落地的设计思想：

- **双工作台架构**：业务前台（Staff 生产为主）与管理后台（Admin 管理为主）分离，按角色给不同视图，避免权限与功能耦合。
- **个性化 + 场景化**：在正确的时间/位置给正确的人递正确的工具，降低信息过载。
- **数字资产管理的「阶段设计」**：售前（价值传递）→ 初始化（预置典型案例，降低门槛）→ 使用（低噪音引流）→ 下线（定期评估，避免僵尸服务拉低整体评价）。
- **Staff vs Admin 视图差异**：Staff 重单对象编辑流（默认隐藏移动/删除等管理动作，选中后才出现）；Admin 重多对象统计与强过滤（默认展示管理型操作 + 全字段筛选）。
- **长表格提效**：字段显隐/排序、自定义列宽、关键列与操作列固定。
- **隐藏提效操作**：框选+快捷键、单元格内快速编辑、拖拽排序。
- **设置「就地管理」**：把设置分散到各功能模块旁，而非集中到一处。
- **AI 辅助定位**：用于非结构化任务（CLIP 图像搜索、自动归档、表单自动填充、规则标准评估），不在强确定性的标准操作里硬塞 AI。

> 对标结论：本项目已具备「双工作台 / 角色壳（platform/client/agent）」的正确骨架（见 AGENTS.md 的 ROLE-SHELL-LOCK-01），**架构方向对，错在视觉层把这些角色壳的配色搞乱了**——这正是 P0 级问题的根因。

## 二、本项目设计系统深度扫描结果

### A. 配色令牌：多套并存、同名不同值（最严重）

#### 前端 `frontend/`（营销站）
同一个语义变量被多次重定义，且**同名不同值**：

| 变量 | 位置 | 值 | 问题 |
|------|------|-----|------|
| `--color-primary` | `assets/css/main.css:4` | `#0f172a`（近黑） | 被当作主按钮背景 |
| `--color-primary` | `assets/css/luna-tokens.css:124` | `teal #0f766e` | 作用域重绑覆盖 |
| `primary`(Tailwind) | `tailwind.config.ts:22` | `#3b82f6`（蓝） | 与上面命名相同，值不同 |
| `--saas-primary` | `assets/css/saas-marketing.css:5` | `#2563eb`（蓝） | 又一套主色 |
| `--b2b-primary` | `assets/css/b2b-industrial.css:7` | `#1e3a5f`（深海军蓝） | 又一套主色 |

> 🔴 **关键冲突**：`main.css` 里 `--color-primary` 是**近黑色 #0f172a**，而 Tailwind 的 `bg-primary` 是**蓝色 #3b82f6**。两处都用「primary」这个名字，但在同一站点会渲染出「黑按钮」和「蓝按钮」两种主操作——这是最刺眼的不一致。

#### 后台 `frontend/admin/`（SaaS 后台）
主色历史上在「紫 → 蓝灰 → 薄荷绿」间反复迁移，残留值散落：

| 来源 | 位置 | 主色值 | 状态 |

| 旧紫/蓝灰 | `uiPreferences.ts:25-35`（LEGACY 集合） | `#7c3aed`/`#6f93ab` 等 | ⚠️ 已迁移但残留 |

### B. 按钮系统：三套并存 + 硬编码冲突

**前端（3 套按钮样式互相不统一）**

## 三、完整改进方案

### 3.1 设计令牌：建立单一真源（Single Source of Truth）

**原则**：删除散落的 5+ 套品牌色，前端/后台各自只保留一份「语义化令牌」，且**前端与后台共享同一套语义命名**。

**前端统一令牌提案**（`frontend/assets/css/main.css` 作为唯一真源，其余文件改为 `@import` 或直接引用，不再重定义）：
```css
:root {
  /* 品牌主色：与后台平台薄荷绿对齐，前端也用同一颗薄荷，避免双品牌认知 */
  --color-primary: #4a9b8c;        /* 原 #0f172a 改为薄荷绿，消除黑按钮 */
  --color-primary-dark: #2a6b60;
  --color-primary-light: #5eb8a8;
  --color-secondary: #2563eb;      /* 蓝，仅作次要/链接色 */
  --color-accent: #10b981;
  /* 语义功能色（前后端共用同一组值） */
  --color-success: #10b981;
  --color-warning: #f59e0b;
  --color-danger:  #ef4444;
  --color-info:    #2563eb;
}
```
- 删除 `luna-tokens.css` 内对 `--color-primary` 的作用域重绑，改为引用同一变量。
- 删除 `--saas-primary` / `--b2b-primary` 独立定义，统一走 `--color-primary`。
- Tailwind `primary` 改为 `#4a9b8c`，与 CSS 变量一致。

**后台统一令牌提案**：以 `design-tokens-v3.scss`（已 LOCKED）为唯一真源，删除 `design-tokens.scss`/`v2` 的旧值引用；`style.css` 里的 `.btn-primary` 改为 `var(--uj-brand)`（或 `--uj-brand-deep`），**删除所有 `#2563eb` 硬编码**；在 `tailwind.config.js` 把 `primary` 指向 `--uj-brand`，废弃 sky/紫/橙旧板。

### 3.2 按钮系统：收敛为一套规范

- **前端**：保留 `components/ui/Button.vue` 作为唯一按钮组件，删除 `main.css`/ `saas-marketing.css` 里的 `.btn-*`/`.saas-btn-*`，统一用 Tailwind class 引用令牌。
- **后台**：保留 Ant `a-button` + mint-glass 覆盖，**删除 `style.css` 里 `.btn-primary`/`.btn-danger`/`.gradient-*` 硬编码类**（或改为引用 `--uj-brand`）。
- **destructive 统一**：所有危险操作走 `var(--color-danger)` / Ant `danger`，不再用 `red-500`。
- **聚焦环统一**：聚焦环颜色跟随当前主色（如 `0 0 0 3px rgb(74 155 140 / .35)`），不再用错位的橙色。
- **主/次操作层级**：主操作（primary）每屏 ≤1 个高亮；次要用 `default`/`text`；破坏性用 `danger`。这与站酷参考中「克制、弱边框、单一主色」一致。

### 3.3 SaaS 交互配色规则

参照站酷文章「双工作台 / 角色壳」思想，建立**角色级 accent + 全局语义色**两层体系：

| 层级 | 规则 | 取值 |
|------|------|------|
| 全局语义色 | 成功/警告/危险/信息，全角色一致 | success `#10b981` / warning `#f59e0b` / danger `#ef4444` / info `#2563eb` |
| 角色壳 accent | platform=薄荷 / client=蓝 / agent=青（已是设计意图） | `#4a9b8c` / `#2563eb` / `#0d9488` |
| 约束 | 角色 accent 只用于「壳级品牌」（顶栏/侧栏 logo/主操作），不污染语义色 | — |
| 用户自定义 | `ThemeSettingsDrawer` 限定在预设调色板内，且对每个候选值做 WCAG AA 对比度校验（白字 on 主色 ≥ 4.5:1） | — |

> 这样既保留「按角色区分配色」的正确设计（对标文章 Admin/Staff 分离），又消除旧硬编码蓝按钮对平台壳的污染。

### 3.4 布局与暗色修复

- **删除死代码**：确认 `MainLayout/Sidebar/Header/ContentArea`（旧 Vben 壳）无引用后归档/删除，保留 `YdPro*` 与 `ClientShellLayout`。
- **前端暗色补全**：为 `assets/css/*` 增加 `[data-theme=dark]` 变量（背景/表面/文字/边框反转），让 `color-mode` 真正生效；或若暂不计划暗色，从 `nuxt.config` 移除该模块避免误导。
- **z-index 集中**：在布局壳统一定义 `--z-sidebar/--z-topbar/--z-drawer/--z-modal` 令牌，避免层级冲突。
- **设置就地管理**：参考文章，把「主题/密度」等设置入口放到对应模块旁，而非全收进一个抽屉（当前 `ThemeSettingsDrawer` 可保留，但补充「就地」入口）。

### 3.5 对比度与一致性校验（落地前必做）

- 用脚本统计两个前端所有硬编码 `#xxxxxx`，聚合后逐个确认是否应改为令牌。
- 对全部「浅灰文字 + 浅底」组合（`#94a3b8`/`#a8b0bb` 等）跑一次 WCAG AA 校验（正文 ≥ 4.5:1，大字 ≥ 3:1）。
- 建立 `tokens` 校验：CI 里加一条 lint，禁止在组件 `<style>`/Tailwind 任意类里出现裸 hex（除令牌文件外）。

### 3.6 落地步骤（建议顺序）

1. **P0（1 天）**：改 `main.css` 的 `--color-primary` 为薄荷绿；删 `style.css` 中 `.btn-primary`/`gradient-*` 硬编码蓝/紫/橙；后台 Tailwind `primary` 指向 `--uj-brand`。→ 消除最刺眼的黑/蓝/绿按钮冲突。
2. **P1（1–2 天）**：收敛前端 3 套按钮为 1 套；修复聚焦环；destructive 走令牌；前端暗色补全或移除模块。
3. **P2（2–3 天）**：删旧布局死代码；建令牌校验 lint；角色 accent 预设调色板 + 对比度约束；长表格/就地设置等站酷文章建议的体验优化。

## 四、结论

- **方向正确，执行混乱**：本项目「薄荷绿平台色 + 角色壳（platform/client/agent）」的架构与站酷企业级 SaaS 文章的主张一致，问题不在设计方向，而在**配色令牌被 5+ 套来源重定义、按钮被 3 套系统实现、且残留了历史紫/蓝灰/蓝/橙硬编码**。
- **最该先修的 3 件事**（P0）：① 前端 `--color-primary` 近黑→薄荷；② 后台 `style.css .btn-primary` 蓝→薄荷；③ 删除 Tailwind/style.css 里的旧紫/蓝灰/橙残留。改完即可消除「同站主色不一致、同壳按钮与主题割裂」的核心观感问题。
- **对标站酷的设计语言**：B 端 SaaS 应「克制——单一主色 + 中性灰 + 极少量功能色」，把 AI/个性化作为增强而非干扰；本项目可在令牌统一后，进一步落地文章建议的「长表格提效、就地管理、阶段化引导」等交互层优化。

> 本报告为只读审计，未改动任何源码。如需我直接执行 P0 修复（改令牌 + 删硬编码），可明确告知，我将进入实施模式并同步更新 AGENTS.md 的设计约定。
