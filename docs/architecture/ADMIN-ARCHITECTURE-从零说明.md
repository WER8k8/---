# 优丁管理后台 · 架构从零说明（给人看，不是改代码）

> **写给谁**：业务负责人、产品、视觉、不用写代码的同事  
> **目的**：从头讲清楚「系统分几层、谁管什么、按什么顺序做」  
> **原则**：在现有工程上**演进**，不是推倒重写  
> **更新**：2026-06-07

---

## 一、一句话

这是一个 **出海营销 SaaS 的管理后台**：用户登录后，左边是菜单，上面是标题和工具，中间是具体业务页面（看板、租户、询盘等）。  
**架构要做的事**：让这些框子稳定、好看、好改，业务页只填「中间内容」，不要每页各搞一套壳。

---

## 二、四层模型（从下往上，像盖楼）

想象一栋四层楼，**只能从下往上建，不能跳层**。

```
┌─────────────────────────────────────────────┐
│  第 4 层 · 体验与送检                        │
│  90 秒演示路径、融资彩排、暗色模式同样能用      │
├─────────────────────────────────────────────┤
│  第 3 层 · 业务页面                          │
│  看板、租户、询盘、财务…（270+ 页的内容区）    │
├─────────────────────────────────────────────┤
│  第 2 层 · 统一外壳（YoudingProLayout）       │
│  侧栏 + 顶栏 + 标签 + 主题 + 搜索 + 通知      │  ← 我们刚拆完这一块
├─────────────────────────────────────────────┤
│  第 1 层 · 规则与清单（设计规范 + 菜单表）      │
│  颜色字号约定、菜单只登记一处、导航怎么算高亮    │
└─────────────────────────────────────────────┘
         ↓ 支撑
┌─────────────────────────────────────────────┐
│  地基 · 后端 API + 数据库（FastAPI，不动大结构） │
└─────────────────────────────────────────────┘
```

**您只需要记住**：  
- 改「长什么样」→ 先看第 1、2 层  
- 改「业务功能」→ 第 3 层  
- 改「演示能不能过审」→ 第 4 层  

---

## 三、外壳里到底有什么（第 2 层，已落成三块）

现在登录后看到的框子，已经拆成 **三个零件**，以后改外观主要动这三处：

| 零件 | 您看到的是什么 | 职责（大白话） |
|------|----------------|----------------|
| **侧栏** | 左边菜单 | 展示菜单、折叠、子菜单、当前选中项 |
| **顶栏** | 上面一条 | 页面标题、搜索、通知、设置、头像 |
| **标签区** | 顶栏下面 | 您的角色名 + 已打开页面的标签页 |

中间空白区域 = **第 3 层业务页**，外壳不管业务逻辑。

---

## 四、菜单只认「一份总表」（第 1 层，防乱）

**问题**：以前菜单写在 layout 大文件里，改一处漏一处，还会闪、高亮错乱。  

**现在的规矩**：

1. **菜单中文名和路径** → 只在一个文件里登记（`platformShellMenu.ts`）  
2. **谁该高亮、标签页显示什么字** → 只在一套「导航算法」里算（`shellNavKernel`）  
3. **外壳组件** → 只负责显示，不再自己写菜单逻辑  

以后加菜单：**先改总表，再跑自动检查**，避免漏路由。

---

## 五、三种角色，一套外壳（还没完全做完）

系统有三种使用者界面，**布局要一样**，只是 **颜色主题和菜单不同**：

| 角色 | 典型用户 | 菜单举例 | 主题色倾向 |
|------|----------|----------|------------|
| **平台超管** | 优丁内部 | 租户、财务、AI 中心 | 薄荷绿 |
| **租户** | 出海企业客户 | 工作台、询盘、产品 | 蓝色 |
| **代理 / 省代** | 渠道伙伴 | 业绩、佣金、开户 | 青绿色 |

**架构目标（第 5 步才做）**：三种角色共用同一套侧栏+顶栏+标签结构，换肤不换布局。  
**不是**再写三套独立后台。

---

## 六、后端在架构里的位置（不重写业务）

- 现有 **FastAPI + 数据库** 继续服务业务（询盘、租户、支付等）  
- 将来如需「按权限动态下发菜单」，会在后端加一层 **Admin BFF**（专门给前台用的薄接口）  
- **顺序**：先把前台菜单总表和外壳定死 → 再写 BFF 契约 → 最后才接动态菜单  
- **禁止**：接口没做好就假装菜单已从服务器下发（假交付）

---

## 七、按顺序走的六步路线图（设计优先，不重写代码）

下面是一根 **单线程顺序**。上一步没定稿，下一步只做准备、不大改。

| 步 | 名称 | 做什么 | 谁牵头 | 您要做什么 |
|----|------|--------|--------|------------|
| **1** | 定规矩 | 颜色、字号、壳层能力清单（已有 LOCKED 文档） | 产品 + 架构 | 知道「薄荷玻璃 + 运营台偏密」即可 |
| **2** | 定外壳长什么样 | 侧栏/顶栏/标签定稿图，三种角色各一张效果图 | **视觉 / 美工** | 看图签字：「就按这个来」 |
| **3** | 定演示脚本 | 90 秒送检点哪几个菜单、每段看什么 | **产品 + 您** | 跟着脚本点一遍，说顺不顺 |
| **4** | 壳层补全 | 三角色同壳换色、主题亮/暗、标签与菜单对齐 | **前端** | 再点菜单，确认不闪、标签中文对 |
| **5** | 标杆页抛光 | 只看 3 页：看板、租户、询盘（送检必看） | **视觉 + 前端** | 看这三页是否「像成品」 |
| **6** | 接口与送检 | BFF 菜单契约（如需）、QA 录屏、门禁脚本 | **架构 + 后端 + QA** | 最后彩排签字 |

**当前进度**：第 1 层 + 第 2 层外壳 **零件已拆好**（步 4 进行了一半）。  
**下一步应该是步 2**：视觉出定稿图，**不是**继续大改代码。

## 八、各部门在第几步上场

| 部门 | 主要参与步骤 | 不负责什么 |
|------|--------------|------------|
| **您（Owner）** | 3、5、6 点头验收 | 不用写代码、不用记文件名 |
| **产品经理** | 1、3、排期、挡 scope | 不代替视觉定稿 |
| **视觉 / 美工** | 2、5 效果图与标杆页清单 | 不改后端接口 |
| **UX / 交互** | 2、3 点击路径、无障碍 | 不批量改 270 页 |
| **架构师** | 1、6 契约与冻结 | 不写业务页 UI |
| **前端** | 4、5 按图实现 | 不在 layout 里再堆菜单 |
| **后端** | 6 BFF（冻结后） | 不重写 FastAPI 业务 |
| **QA** | 4、6 自动检查 + 录屏 | 不修功能，只报问题单 |
| **合规 / SaaS 专家** | 6 送检前扫 Stub | 不参与日常改样式 |

## 九、和「代码重写」的边界（请放心）

| 会做的（演进） | 不会做的（重写） |
|----------------|------------------|
| 外壳拆零件、统一菜单总表 | 换框架、换 Vue、换 Ant Design |
| 三角色同壳换色 | 270 页 simultaneous 重写 |
| 3 个标杆页抛光 | 全站 overnight 换肤 |
| BFF 加薄接口 | 后端业务 API 推倒重来 |

---

## 十、您现在只需记三句

1. **系统 = 外壳（框） + 业务页（中间） + 后端（数据）**  
2. **顺序 = 先定外观图 → 再补壳 → 再抛光 3 页 → 最后送检**  
3. **壳层代码已拆好，下一步等视觉定稿，不是继续盲改代码**
